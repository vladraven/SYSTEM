2. Architecture Principles

Система должна проектироваться не как “умный прогнозатор”, а как прозрачный, аудируемый и детерминированный механизм оценки макроэкономических рисков на основе явно заданных данных, правил, конфигураций, версий и ограничений.

Система должна отдавать приоритет:

Correctness over feature count.
 Корректность важнее количества функций.

Transparency over automation.
 Пользователь должен понимать, какие данные, веса, правила, версии и ограничения повлияли на результат.

Deterministic behavior over heuristics.
 Одинаковые входные данные должны всегда давать одинаковый результат.

Auditability over convenience.
 Удобство разработки или использования не должно разрушать воспроизводимость и audit trail.

Modularity over monolithic implementations.
 Система должна быть разделена на независимые, тестируемые и заменяемые компоненты.

Explicit failures over silent recovery.
 Если данные отсутствуют, источник устарел, лицензия не подтверждена или validation failed, система должна явно сообщить об этом, а не “исправлять” проблему молча.

Explainability at every layer.
 Каждый production score, dashboard state, report и backtest result должен быть объясним через сохранённые данные, configuration version, weights, thresholds, validation metadata и model rules.

Обязательный архитектурный принцип:

Every production decision must be reproducible.

3. Non-Goals

Система не предназначена для того, чтобы:

Предсказывать рецессии.
Гарантировать раннее обнаружение кризисов.
Превосходить профессиональные macroeconomic forecasting models.
Заменять econometric research.
Делать causal inference без явной методологической поддержки.
Восстанавливать или “угадывать” недоступные данные.
Нарезать исторические кризисы на искусственные подэпизоды ради увеличения N в backtest.
Генерировать probabilistic forecasts на основе недостаточного количества исторических эпизодов.
Использовать generative AI как production decision engine.
Автоматически принимать финансовые, инвестиционные, регуляторные или стратегические решения.
Представлять model-derived estimates как наблюдаемые факты.
Скрывать data quality limitations за красивым dashboard.
Использовать прямые CMHC или CREA источники как production default, если доступны StatCan/Open Government equivalents.

Обязательное правило:

The system must not pretend to know what the data cannot support.

4. Scientific Integrity

Система работает с макроэкономическими данными и model-derived risk scores, поэтому она должна соблюдать принцип научной и методологической честности.

Система должна явно различать:

Observation.
 Наблюдаемое значение из источника данных.

Transformation.
 Производное значение после нормализации, frequency alignment, forward-fill или другой детерминированной обработки.

Model output.
 Результат Risk Engine, полученный по правилам модели.

Interpretation.
 Текстовое объяснение того, что может означать model output.

Hypothesis.
 Предположение, которое может использоваться для анализа, но не является доказанным фактом.

Обязательные правила:

Система не должна подразумевать causal inference, если причинно-следственная связь явно не установлена и не задокументирована.
Система не должна представлять risk score как наблюдаемое измерение.
Система не должна представлять backtest на малой выборке как статистически надёжное доказательство качества модели.
Система не должна скрывать методологические ограничения.
Система должна ясно отделять данные от модели и интерпретации.
Любой narrative report должен использовать осторожный язык.
Любой dashboard должен визуально отличать observed data, transformed values и model-derived outputs.
Любой report должен избегать формулировок, которые звучат как прогноз, доказательство или causal claim.

Допустимые формулировки:

The model-derived risk score increased from moderate to high based on the configured indicators and weights.
This suggests elevated macroeconomic stress under the current configuration.
The result should be interpreted as a model-based diagnostic, not as a forecast or causal conclusion.

Недопустимые формулировки:

The economy will enter a recession.
The model proves that inflation caused the risk increase.
The backtest confirms 80% recall.
The model guarantees a recession warning.
The system predicts with confidence.

Нужно реализовать ScientificIntegrityGuard.

ScientificIntegrityGuard должен проверять:

narrative reports;
dashboard summaries;
exportable text;
production report templates;
approved narrative slots.

ScientificIntegrityGuard должен использовать case-insensitive regex matching.

Если banned phrase обнаружена:

Генерация или публикация отчёта блокируется.
Возвращается error_code = SCIENTIFIC_INTEGRITY_VIOLATION.
Нарушающая фраза и контекст записываются в audit trail.
Report или slot не может быть опубликован, пока текст не исправлен и не переутверждён Risk Officer.

Минимальный banned-phrases list:

will enter recession
proves that
confirms 80% recall
guarantees
predicts with confidence
recession is certain
model proves
statistically confirms, если N < 10
caused by, если causal claim явно не разрешён

Обязательный научный инвариант:

Every score is a model-derived estimate, not an observed measurement.

5. Separation of Data, Model and Interpretation

Система должна физически и логически разделять три слоя.

5.1 Data Layer

Data Layer отвечает только за:

Получение данных.
Проверку источников.
Хранение vintages.
Хранение release metadata.
Хранение ingestion metadata.
Хранение revision history.
Хранение license metadata.
Хранение data quality flags.

Data Layer не должен делать экономические выводы.

5.2 Model Layer

Model Layer отвечает за:

Frequency alignment.
Missing indicator handling.
Weight normalization.
Indicator normalization.
Risk score calculation.
Category score calculation.
Backtest evaluation.
Reliability flags.
Model-derived diagnostic outputs.

Model Layer не должен скрывать uncertainty, validation warnings или data quality limitations.

5.3 Interpretation Layer

Interpretation Layer отвечает за:

UI explanations.
Narrative reports.
Situation Room summaries.
Human-readable warnings.
Documentation of limitations.

Interpretation Layer не должен создавать новые факты, новые данные, новые forecasts или новые causal claims.

6. System Invariants

Следующие инварианты являются обязательными математическими и архитектурными правилами системы. Любое нарушение считается ошибкой реализации.

6.1 Risk Score Invariants
Risk score всегда находится в диапазоне 0 <= risk_score <= 100.
Risk score не рассчитывается, если доступно 0 индикаторов.
Production score не может быть рассчитан без validation metadata.
Production score не может использовать series со статусом requires_license, unverified, series_mapping_stale, access_denied, pending_validation или temporary_unavailable.
Каждый score должен быть воспроизводим из configuration_version, vintage_date, stored data vintages, indicator values, normalized indicator scores, original weights, effective weights, risk thresholds, source validation metadata, license metadata и model version.
6.2 Coverage Invariants

Production score рассчитывается только если одновременно выполнены условия:

coverage_ratio >= 60%.
Все required indicators доступны.
Доступно минимум 3 indicators.
Ни один используемый indicator не имеет license_status = requires_license или unverified.
Ни один используемый indicator не имеет validation_status = pending_validation, series_mapping_stale, access_denied или temporary_unavailable.

coverage_ratio считается по original weights, а не по количеству индикаторов и не по discounted weights.

Формула:

coverage_ratio = сумма original_weight доступных eligible indicators / сумма original_weight всех configured indicators × 100%.

Так как сумма configured weights должна быть равна 100%, практически:

coverage_ratio = сумма original_weight доступных eligible indicators.

frequency_discount не влияет на coverage_ratio. Он применяется только позже, при расчёте effective_weight внутри Risk Engine.

Если отсутствует required indicator:

production calculation_status = insufficient_data;
coverage_ratio можно показать информационно;
production score не рассчитывается.

Исключение:

single_indicator_diagnostic разрешён только для draft, experimental или sandbox mode. Он никогда не может быть production score и никогда не может отображаться в production Situation Room.

6.3 Weight Invariants
Все веса должны быть неотрицательными.
Negative weights запрещены.
Сумма configured weights в валидной production configuration должна быть равна 100%.
Если часть индикаторов отсутствует, сумма effective weights среди доступных eligible indicators должна быть равна 100%.
Missing indicator не может быть интерпретирован как zero contribution.
frequency_discount применяется к effective_weight, но не изменяет original_weight и не изменяет coverage_ratio.
6.4 Decimal Calculation Invariants

Все математические вычисления весов, нормализации, effective weights, contribution values и итогового risk_score в PHP должны производиться строго через bcmath functions или специализированный Decimal Value Object.

Запрещено:

Использовать native PHP float для risk score calculations.
Использовать автоматическое преобразование DECIMAL strings из MySQL в float.
Выполнять операции +, -, *, / над decimal strings без bcmath или Decimal Value Object.
Округлять intermediate values раньше финального этапа расчёта.

Обязательные требования:

MySQL DECIMAL values должны считываться как strings.
Arithmetic layer должен работать со строковыми decimal values.
Финальное округление должно происходить только при сохранении результата в DECIMAL(10,4).
Все tests для Risk Engine должны проверять отсутствие float drift.
6.5 Data Invariants
Нельзя использовать данные, недоступные на vintage_date.
observation_date не равна автоматически release_date.
Если official release_date отсутствует, но данные были использованы в production calculation, система должна сохранить estimated_release_date = ingestion_date, release_date_quality = fallback_to_ingestion и release_date_source = system_inferred.
Latest revised value нельзя использовать в historical backtest, если эта revision не была доступна на соответствующую historical vintage_date.
External series mapping не может считаться production-valid без успешной source validation.
Stale source mapping должен явно блокировать production use.
Историю данных нельзя перезаписывать без audit record.
Snapshot deduplication должна предотвращать дублирование неизменившихся наблюдений.
frequency_at_observation должен храниться на уровне observation/vintage, а не только series.
6.6 Configuration Invariants
Published configuration version immutable.
System Preset — это curated, immutable, production-approved RiskConfigurationVersion.
RiskConfiguration — это логическая сущность, которая может иметь много версий.
RiskConfigurationVersion — это неизменяемый snapshot настроек.
Любое изменение published RiskConfigurationVersion создаёт новую version.
Backtest result всегда привязан к конкретной RiskConfigurationVersion.
Нельзя использовать backtest одной версии configuration для публикации другой версии.
System Presets могут содержать только production-eligible series.
6.7 Reporting Invariants
Narrative reports должны быть детерминированными.
Production reports не должны зависеть от runtime LLM.
Reports должны включать warnings, если score рассчитан на неполном наборе индикаторов.
Reports должны включать small-sample warning, если backtest основан на N < 10.
Reports не должны представлять model output как empirical fact.

10. Official Data Sources

Раздел официальных источников должен содержать только реальные официальные ресурсы. Запрещено включать в official sources блоги, stock image sites, PyPI packages, GitHub wrappers, commercial data mirrors или неофициальные tutorials.

Все источники являются candidate sources, а не trusted production mappings. Любой table ID, vector ID, series ID, URL или endpoint должен быть проверен live-запросом перед включением в production registry.

10.1 Statistics Canada

Statistics Canada Web Data Service должен использоваться как основной источник канадских макроэкономических series, включая CPI, labour market, GDP, retail sales, household indicators и housing indicators. WDS является RESTful web data service over HTTPS и возвращает данные в JSON.

Официальная документация:

Statistics Canada WDS User Guide: https://www.statcan.gc.ca/en/developers/wds/user-guide.
Statistics Canada API overview: https://www.statcan.gc.ca/en/microdata/api.

Statistics Canada API overview перечисляет WDS methods, включая getCubeMetadata, getSeriesInfoFromVector, getDataFromVectorsAndLatestNPeriods, getDataFromVectorByReferencePeriodRange и getFullTableDownloadCSV.

Правило для Statistics Canada mappings:

Нельзя hardcode-ить table IDs как production truth.
Любой table ID в спецификации является discovery candidate only.
Любой candidate table ID должен пройти getCubeMetadata.
Любой vector ID должен пройти getSeriesInfoFromVector.
Любой data pull должен проверять schema, frequency, latest reference period, issueDate или release metadata, если доступно.
Если API возвращает 404, 409, inactive, schema mismatch или устаревший payload, series получает validation_status = series_mapping_stale или temporary_unavailable в зависимости от причины.
10.2 Bank of Canada

Bank of Canada Valet API должен использоваться как основной источник financial conditions data, включая exchange rates, policy rates, yields, selected economic statistics and financial statistics. Valet API предоставляет endpoints для lists, series, observations, groups и group observations.

Официальная документация:

Bank of Canada Valet API docs: https://www.bankofcanada.ca/valet/docs.
Bank of Canada Valet API how-to: https://www.bankofcanada.ca/valet-api-how-to/.

Bank of Canada Valet API how-to указывает, что registration/key не требуются, но нужно учитывать request limits, caching и processing delays.

Candidate financial conditions series from Bank of Canada:

Policy interest rate.
Overnight rate.
Treasury bill yields.
Government of Canada bond yields.
Yield curve spread.
CAD/USD exchange rate.
Other CAD exchange rates, если нужны.
Monetary policy related series.
Financial market stress proxies, если доступны и license_status позволяет production use.

Правило для Bank of Canada mappings:

Нельзя считать seriesName валидным без запроса к series endpoint.
Нельзя использовать observations без проверки frequency, latest date, response schema и missing values.
Если Valet API временно не вернул свежие данные из-за processing delay, series должна быть marked as data_pending или update_delayed, а не automatically stale.
Если series не существует, deprecated, moved или response schema изменилась, series должна быть marked as series_mapping_stale.
10.3 Statistics Canada Housing and Residential Real Estate Data

Statistics Canada должен быть основным production-candidate источником для housing and residential real estate indicators. Direct CMHC and CREA sources must not be used as default production sources.

Statistics Canada Housing Statistics hub содержит housing statistics, housing market indicators, New Housing Price Index dashboard, Residential Property Price Index tool, Canadian Housing Statistics Program and Canadian Housing Survey materials.

New Housing Price Index должен использоваться как replacement candidate for CREA HPI for new-home price pressure. Statistics Canada указывает, что New Housing Price Index measures changes over time in contractors’ selling prices of new houses, and the dashboard references Table 18-10-0205-01 and Table 18-10-0205-02. Эти table IDs являются discovery candidates only и должны пройти live validation.

Residential Property Price Index должен использоваться как broader housing price candidate indicator, потому что RPPI covers both new and resale properties and includes house and condominium apartment markets for selected CMAs. The dashboard references Table 18-10-0169-01 and Table 18-10-0171-01. Эти table IDs являются discovery candidates only и должны пройти live validation.

RPPI resale components must go through terms review, because Statistics Canada states that resale residential property price indexes are produced jointly by Teranet and National Bank of Canada and licensed to Statistics Canada for publication and distribution.

Housing starts, under construction and completions can be sourced through StatCan/Open Government published table 34-10-0126-01 for annual all-areas data, with geography, housing estimate and type-of-unit dimensions. This table ID is a discovery candidate only and must be live-validated before production use.

10.4 Explicit replacement rule for CMHC and CREA

Direct CMHC data and CREA HPI data must not be part of the default production source list.

Instead:

Replace direct CMHC housing starts/completions dependency with StatCan/Open Government published tables for housing starts, completions, building permits and investment in building construction.

If RPPI includes resale components licensed to Statistics Canada by Teranet/National Bank, store source_provider = Statistics Canada, underlying_origin = Teranet / National Bank of Canada if applicable, license_status = unverified until terms review, production_allowed = false until validation and terms review pass.
CREA HPI must be excluded from System Presets entirely unless a future license review explicitly approves it.
Direct CMHC endpoints, portals, wrappers or Excel downloads must not be used as production ingestion sources if equivalent StatCan/Open Government table access exists.
If no StatCan equivalent exists for a specific housing indicator, the indicator remains excluded from production presets or marked as experimental until source, license and methodology review are complete.

12. Production Eligibility

Production-eligible означает, что entity, configuration или result может использоваться в production score, published dashboard, automated production report или System Preset.

Series является production-eligible только если:

license_status = public_open.
validation_status = valid.
source validation metadata exists.
terms_of_use_url stored, if available.
attribution metadata stored, if required.
release cadence known or explicitly marked unknown_with_manual_review.
frequency known.
transformation_type known.
normalization method and thresholds defined.
no stale mapping.
no access denied.
no pending validation.
no temporary unavailable state.
live validation completed successfully.

Production configuration может публиковать только пользователь с ролью Admin или Risk Officer.

Обычный Analyst может создавать draft и experimental configurations, но не может публиковать production configuration без approval.

Viewer не может создавать, изменять или публиковать configurations.

13. Bootstrap / Cold Start Policy

В первые недели после установки большинство series может находиться в статусе pending_validation. Это нормальное состояние.

Чтобы система могла стартовать без нарушения production rules, вводятся следующие режимы.

13.1 Bootstrap mode

bootstrap mode разрешён только до публикации первого production System Preset.

В bootstrap mode можно:

Создавать candidate sources.
Создавать draft System Presets.
Загружать данные.
Выполнять source validation.
Запускать draft risk score calculations.
Запускать diagnostic calculations.
Создавать draft configurations.
Создавать ReleaseCalendar records.
Выполнять schema validation.
Проверять формулы Risk Engine на synthetic fixtures.
Заполнять official data source registry.
Создавать initial Admin и базовые роли.

В bootstrap mode нельзя:

Публиковать production score.
Публиковать production dashboard.
Публиковать automated production report.
Выдавать draft score как production-ready.
Помечать pending_validation series как valid без live validation.
Использовать unverified или requires_license series в production.
Превращать bootstrap calculation в production calculation задним числом.
13.2 Поведение системы первые 14 дней после установки

День 0–2:

Разрешено только создание пользователей, ролей, sources, endpoints и candidate series.
Production score полностью заблокирован.
Все расчёты только draft или sandbox.
UI/API должны показывать статус system_bootstrap.

День 3–7:

Разрешены ingestion jobs и source validation jobs.
Разрешено создавать draft System Preset.
Разрешено запускать draft calculations.
Запрещено публиковать production score, если не выполнены условия первого production System Preset.

День 8–14:

Разрешено публиковать первый production System Preset только при выполнении всех условий production eligibility.
Если условия не выполнены, система остаётся в bootstrap mode.
Risk Officer не может вручную обойти pending_validation для production.
Risk Officer может утвердить fallback release calendar policy, но не может утвердить unvalidated series как valid без live validation.
13.3 Первый production System Preset

Первый production System Preset может быть опубликован только когда:

Минимум 5 series имеют validation_status = valid.
Минимум 5 series имеют license_status = public_open.
Минимум 5 series имеют хотя бы одно успешно ingested observation.
Минимум 3 indicators доступны на выбранную production vintage_date.
Все required indicators в preset доступны.
coverage_ratio >= 60%.
ReleaseCalendar заполнен или имеет approved fallback policy.
Risk Officer подтвердил production eligibility.
Audit trail содержит запись о публикации preset.
Worked Example для Risk Engine реализован как test fixture.
Source validation history сохранена.
Все series в preset имеют source validation result не старше 30 дней.

Запрещено:

Публиковать первый production System Preset с pending_validation series.
Публиковать первый production System Preset с unverified или requires_license series.
Публиковать production score только ради демонстрации системы.
Понижать required indicator до non-required только для прохождения coverage gate без audit reason.
13.4 Grace period для новых series

Новая series в течение первых 7 дней после регистрации может иметь статус data_pending, если:

source validation прошла успешно;
endpoint существует;
schema валидна;
данных ещё нет из-за ожидаемого release schedule.

После 7 дней отсутствие данных должно перейти в один из статусов:

missing_no_historical_data;
source_unavailable;
series_mapping_stale;
release_late;
temporary_unavailable.

Grace period не делает series production-eligible. Он только предотвращает ошибочную классификацию новой series как stale до первой expected release date.

safe_max.

16.3 normalization_method enum

Production default на MVP:

Архитектура должна поддерживать расширение через NormalizationStrategy.

Обязательные интерфейсные принципы NormalizationStrategy:

Каждая стратегия получает transformed_value, thresholds, direction_of_deterioration и metadata.
Каждая стратегия возвращает normalized_indicator_score в диапазоне 0–100.
Каждая стратегия должна быть детерминированной.
Каждая стратегия должна иметь собственный validator.
Каждая стратегия должна иметь собственные unit tests.
Каждая стратегия должна сохранять параметры расчёта в risk_score_indicator_contributions.
Добавление новой стратегии не должно требовать переписывания Risk Engine.

Зарезервированные стратегии для будущих версий:

Эти стратегии не должны использоваться в production, пока не реализованы, не протестированы и не утверждены в model_versions.

16.4 direction_of_deterioration enum

Допустимые значения:

higher_is_riskier.
lower_is_riskier.
distance_from_target_is_riskier.
outside_band_is_riskier.
16.5 Default normalization method: threshold_linear

Default production normalization method:

threshold_linear.

For higher_is_riskier:

raw value <= low_risk_threshold gives normalized_indicator_score = 0.
raw value >= high_risk_threshold gives normalized_indicator_score = 100.
values between thresholds are linearly interpolated.

For lower_is_riskier:

raw value >= low_risk_threshold gives normalized_indicator_score = 0.
raw value <= high_risk_threshold gives normalized_indicator_score = 100.
values between thresholds are linearly interpolated.

For distance_from_target_is_riskier:

target_value and max_deviation must be defined.
max_deviation must be greater than 0.
score = abs(value - target_value) / max_deviation × 100, clamped to 0–100.

For outside_band_is_riskier:

safe_min and safe_max must be defined.
safe_min must be lower than safe_max.
values inside safe band score 0.
values outside safe band scale toward 100 based on configured boundary thresholds.
16.6 Threshold validation

Для normalization_method = threshold_linear обязательно:

low_risk_threshold != high_risk_threshold.

Если low_risk_threshold = high_risk_threshold, validation должна завершиться ошибкой:

INVALID_CONFIGURATION_THRESHOLDS.

Additional validation constraints:

Для higher_is_riskier: high_risk_threshold должен быть больше low_risk_threshold.
Для lower_is_riskier: high_risk_threshold должен быть меньше low_risk_threshold.
Для distance_from_target_is_riskier: target_value и max_deviation обязательны, max_deviation > 0.
Для outside_band_is_riskier: safe_min и safe_max обязательны, safe_min < safe_max.
clamp_min должен быть меньше clamp_max, если оба заданы.
16.7 Risk score formula

For each available eligible indicator:

raw_value is selected according to vintage_date and frequency alignment.
transformed_value is calculated based on transformation_type.
normalized_indicator_score is calculated by selected NormalizationStrategy.
coverage_ratio is calculated from original_weight only.
frequency_discount is applied after coverage validation.
effective_weight is calculated after missing indicator handling and frequency discount adjustment.

Overall risk_score formula:

risk_score = sum(normalized_indicator_score_i × effective_weight_i / 100)

Category score formula:

Within each category, available indicator weights are re-normalized to 100%.
category_score = sum(normalized_indicator_score_i × effective_weight_i_within_category / 100).
Category contribution to overall score is based on the category’s original configured proportion in the full configuration.

Every calculation result must store:

raw_value.
transformed_value.
normalized_indicator_score.
original_weight.
frequency_discount.
effective_weight.
normalization_method.
thresholds used.
direction_of_deterioration.
source data vintage.
calculation explanation.
16.8 Risk bands

Default risk bands:

0–20: very_low.
21–40: low.
41–60: moderate.
61–80: high.
81–100: severe.

Risk band thresholds may be configurable, but must be versioned and auditable.

Все content_hash и source_payload_hash хранить как CHAR(64), SHA-256.
Все production-critical history tables append-only.
JSON columns использовать только для metadata, diagnostics и audit diffs.

31. Release Date Fallback and Reproducibility

Чтобы не нарушать инвариант Every production decision must be reproducible, запрещается раздвоение логики между current production calculation и historical reproduction.

Если official release_date отсутствует, но данные были использованы в production calculation, система должна сохранить:

estimated_release_date = ingestion_date.
release_date_quality = fallback_to_ingestion.
release_date_source = system_inferred.
reproducibility_allowed = true.

Такой data point может использоваться для воспроизведения того production score, который был рассчитан в прошлом.

Но в методологических предупреждениях должно быть явно указано:

Release date was not provided by source. Ingestion timestamp was used as estimated release date for reproducibility.

Для historical backtest, который претендует на строгую методологическую чистоту, такие точки должны иметь reliability warning:

release_date_estimated.

32. Frequency Alignment Matrix

Base scoring frequency for production:

monthly.

32.1 Daily to monthly
Use last observation released on or before vintage_date.
Do not average by default.
If average is required, it must be explicit in transformation_type.
32.2 Weekly to monthly
Use last observation released on or before vintage_date.
Do not interpolate.
32.3 Monthly to monthly
Use latest monthly observation officially released on or before vintage_date.
If current month data is not released yet, forward-fill previous released month.
32.4 Quarterly to monthly
Use latest quarterly observation officially released on or before vintage_date.
Forward-fill across months until a newer quarter is officially released.
Do not estimate missing quarter.
If detection window is monthly but indicator is quarterly, the same quarterly value may appear across multiple monthly vintage points, with clear forward_fill metadata.
32.5 Annual to monthly
Use latest annual observation officially released on or before vintage_date.
Annual indicators must be marked low_frequency.
Annual indicators cannot have original_weight > 15.0000 in production configuration unless Risk Officer override exists.
Annual indicators may use frequency_discount, but this discount applies only to effective_weight, not coverage_ratio.
32.6 Irregular to monthly
Each irregular series must define validity_window_days.
If latest observation is older than validity_window_days, mark as stale.
If no validity window is defined, irregular series cannot be production-eligible.
32.7 Cold start rule

If no observation exists on or before vintage_date, mark indicator as missing_no_historical_data and exclude it from calculation. If it is required, return insufficient_data.

For new series within 7-day grace period, status may be data_pending instead of missing_no_historical_data if validation succeeded and release is expected.

32.8 Frequency change rule

If a series changes frequency over time, store frequency_at_observation in data_observations and use the frequency valid at observation_date.

33. Missing Indicator Handling

If indicators are missing:

Exclude unavailable non-required indicators from calculation.
Re-normalize weights of available eligible indicators to 100%.
Store original_weight and effective_weight.
Show warning.
Store missing reason.

Missing reasons:

missing_no_historical_data.
release_not_yet_available.
source_unavailable.
stale_mapping.
license_blocked.
access_denied.
schema_mismatch.
required_indicator_missing.
temporary_unavailable.
release_date_unknown.

If required indicator is missing:

production score returns insufficient_data.
draft score may be calculated only if explicitly allowed and marked low_reliability_diagnostic.

Minimum production coverage:

coverage_ratio must be >= 60%.
required indicators must be present.
at least 3 indicators must be available.
all used indicators must be production-eligible.

36. Backtest and Episode Detection

Historical Risk Backtest is diagnostic, not statistical proof.

36.1 Episode model

Each episode must include:

episode_key.
display_name.
start_date.
end_date.
stress_type.
expected_macro_signature.
severity_label.
source_notes.
inclusion_rationale.
detection_threshold_score.
detection_threshold_band.
detection_window_before_days.
detection_window_after_days.
minimum_persistence_periods.
36.2 Detection rule

Default detection rule:

An episode is detected if risk_score >= detection_threshold_score or risk_band >= detection_threshold_band for at least minimum_persistence_periods within the detection window.

Default detection window:

Start: episode start_date minus 90 days.
End: episode end_date plus 90 days.

For quarterly episodes or quarterly-only configurations:

Detection window may be expanded to align with quarterly vintage points.
The expansion must be explicit in episode configuration.
It must be stored in historical_episodes.
It must be shown in backtest results.

Default threshold:

detection_threshold_score = 61.0000.
detection_threshold_band = high.
minimum_persistence_periods = 1 monthly period.

Lead/lag definition:

If first detection date < episode start_date, lead_days = episode start_date - detection_date.
If first detection date >= episode start_date, lag_days = detection_date - episode start_date.
If no detection occurs in window, detected = false.

Rules:

Do not split one macroeconomic episode into subepisodes merely to increase N.
Do not show isolated precision/recall when N < 10.
Always show absolute counts.
N < 10 requires small-sample warning.
Backtest result must be linked to exact configuration version.
Backtest must not be described as forecasting proof.

Required warning:

Warning: Evaluation sample size is too small (N < 10). Metrics are indicative and statistically unreliable.

50. Final Instruction to Agent

Implement incrementally and defensively.

Do not optimize for impressive breadth.

Optimize for:

correctness;
deterministic behavior;
auditability;
reproducibility;
scientific integrity;
source validation;
license safety;
honest backtesting;
no fake precision;
no look-ahead bias;
clear API and UI warnings;
framework-independent PHP architecture;
MySQL-first storage design;
decimal-safe arithmetic;
green CI gates by release milestone.

If uncertain, choose safer behavior:

Mark data as stale rather than silently accepting it.
Block production publish rather than allowing restricted data.
Show absolute counts rather than misleading percentages.
Return insufficient_data rather than calculating misleading score.
Preserve vintage history rather than overwriting values.
Split work into phases rather than generating shallow stubs.
Do not make causal claims without explicit methodology.
Do not present model output as empirical fact.
Do not use generative AI as production decision engine.
Do not use Laravel or Laravel-specific abstractions.
Do not use direct CMHC or CREA production sources when StatCan/Open Government equivalents exist.
Do not trust any table ID, vector ID or endpoint until live validation succeeds.
Do not use unofficial wrappers as production dependencies.
Do not use PostgreSQL-specific assumptions.
Do not use FLOAT for economic calculations.
Do not use native PHP float in Risk Engine.
Do not let frequency_discount reduce coverage_ratio.
Do not publish production score during bootstrap mode.

This system must be reliable, testable, reproducible and honest about data limitations. It should help users understand macro risk diagnostics, but it must not create the illusion of forecast certainty, causal proof or statistical precision where the data does not support it.
